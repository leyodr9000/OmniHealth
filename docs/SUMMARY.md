# OmniHealth 项目总结（v2.3.0）

## 一句话

一个本地优先的 Android 健康记录应用：记录 → 汇总 → 趋势 → 建议全部在本机完成，
在线 AI 是可选项而不是依赖项。

## 两个阶段

### 第一阶段：把功能做全（M0–M9）

数据层（211 条食物字典）→ 计算引擎（BMI/BMR/TDEE/5 维评分/步数）→ UI 组件 →
首页真实数据 → 饮食运动 → 五类图表 → AI（云 + 离线规则引擎）→ 设置/习惯/提醒 →
签名包/启动图/CSV 导出。

期间做过一次性能整改：包体 18.87 MB → 1.96 MB，冷启动 ~1.06 s → ~0.33 s，
手段是 release + R8、WorkManager 按需初始化、去 graphicsLayer、SQL 范围聚合。

### 第二阶段：按评估方案治理质量

评估文档指出「功能覆盖广但仍是未验证的原型」，于是按 P0→P4 重做了一遍：

| 阶段 | 关键改动 | 验证方式 |
|---|---|---|
| P0 数据正确性与隐私 | 去静默清库、缺失维度不按 0 分、模拟数据隔离、CSV 注入防护、Key 加密 | 单测 + 首页零数据实测 |
| P1 记录管理与备份 | 删除撤销、历史补录、点击编辑、系统分享、JSON 备份/事务恢复 | 模拟器端到端（138→0→138、249 kcal 补录隔离、300→350 g） |
| P2 统一体验 | 五栏导航、未记录≠0、inset 单一归属、1.3× 字体、横屏、深色模式、滚动保留 | 模拟器实测逐项 |
| P3 分析可信度 | 参考分披露参与度、AI 来源/覆盖/缺口、首次发送确认、明文接口拦截 | 报告文案实测 + 4 个端点单测 |
| P4 发布治理 | 25 单测、验收清单、迁移实测、真机性能协议 | 升级测试（v2.0.0→v2.1.0 数据保留） |

## 抓到的真实缺陷

1. **升级闪退**：DB v1→v2 迁移漏了 `workouts` 表的 `ALTER`，升级即崩。这是「迁移必须实测」的直接证据。
2. **今日记录被埋**：录完的食物排在 40 条字典之后，实际不可见。
3. **缺失值被当 0**：没记录睡眠会按「睡了 0 小时」扣分，分数失真。
4. **静默清库**：`fallbackToDestructiveMigration()` 会在迁移失败时抹掉全部健康数据且无提示。
5. **密钥明文**：API Key 原样存在 DataStore，导出与备份都可能带出去。

## 设计上的三个判断

- **默认 Material 3，液态玻璃作为可选项**：模糊背景会降低长文本可读性，不能当默认。
- **不升级 Compose 去追官方 miuix**：其最新版要求 Compose 1.12 + Kotlin 2.4，收益不抵风险，改为自建两套视觉。
- **缺失不等于零，不可信就不给分**：维度不足一半时显示「数据不足」，而不是编一个精确总分。

## 明确没做到

| 项 | 状态 |
|---|---|
| 真机性能数据 | 未采集，需物理设备；协议已备 |
| 键盘弹起 / TalkBack | 未验证，无头模拟器无法覆盖 |
| 恢复流程端到端 | 只验证了文件与事务逻辑，SAF 无法脚本化 |
| 时区回溯、收藏、复制上一餐 | 未做，属增强项 |

## 结论

从「功能齐全的原型」推进到了「数据口径明确、记录可维护、结论有出处、失败不丢数据」的状态。
剩下的都是需要真机或属于功能扩张的项，不再是正确性问题。
