# AI 融合执行状态（v3.3.0 收尾）

对照《OmniHealth AI 功能融合与 UI 调整方向》逐条核对**当前代码**。

| 要求 | 现状 | 证据 |

## 二、四个功能方向

### 第一批 智能记餐 ✅ v3.0.0

流程：描述 → 识别 → 匹配候选 → 用户校对 → 保存。

| 关键规则 | 实现位置 |
|---|---|
| AI 只识别/匹配，不产生营养值 | `MealParser` 只输出「食物 + 克数」 |
| 营养来自有来源的资料 | 由食物表 × 克数计算后写入 `DietLogEntity` |
| 模糊份量展示假设并可改 | 一碗/两个按「一份」换算，UI 可 ±25 g |
| 匹配不确定不伪装 | 未匹配显示「未匹配到食物」，且不进入保存 |
| 确认前不写库 | 只有「保存 N 条」才调用 `logFood` |
| 保留确定性入口 | 搜索与字典入口未改动 |

单测：`MealParserTest` 6 个。

### 第二批 趋势解读 ✅ v3.1.0

趋势页展示体重 / 摄入 / 步数三张卡：结论 → 依据 → 限制。

| 关键规则 | 实现位置 |
|---|---|
| 均值、变化量由程序算 | `TrendInterpreter.compareWeeks` |
| 缺失不当零 | 序列为 `List<Float?>`，单测断言 5 天记录时均值仍接近真实值 |
| 覆盖不足只说明缺什么 | 两周各需 ≥4 天，否则输出「数据不足」 |
| 不做因果解释 | 文案只讲方向与幅度 |
| 标明区间与覆盖度 | 依据行写出两侧天数与均值 |

单测：`TrendInterpreterTest` 4 个。

### 第三批 周复盘与行动 ✅ v3.2.0

趋势页复盘卡：本周变化 → 数据依据 → 一条行动。

| 关键规则 | 实现位置 |
|---|---|
| 「未记录早餐」≠「没吃早餐」 | `WeeklyReview` 文案固定为「没有早餐记录」；单测断言不含「没吃」 |
| 行动连接真实功能 | `OPEN_RECORDS` → 记录页；`OPEN_REMINDERS` → 设置页 |
| 不自动改目标 | 没有写目标的代码路径 |
| 避免惩罚式文案 | 稳定的一周直接建议「暂不调整目标」 |

单测：`WeeklyReviewTest` 5 个。

### 第四批 场景搭配 ✅ v3.3.0

饮食页「帮我搭配」：3 个候选（主食 + 蛋白 + 蔬果）。

| 关键规则 | 实现位置 |
|---|---|
| 约束由规则校验 | `MealPlanner` 按类别筛选 + 禁忌关键词硬过滤 |
| 营养由程序计算 | 食物表 × 克数 |
| 计划 ≠ 已吃 | 候选只在内存，点「就吃这一餐」才写库 |
| 不用剩余全量当一餐 | 预算 = 今日剩余 ÷ 3，夹在 300–900 kcal |
| 标注估算属性 | 每张卡带「按参考份量估算」 |

单测：`MealPlannerTest` 5 个。

## 三、职责边界（方案第八节）

代码中不存在「模型直接写库」的路径：

- 在线 AI 只用于周报/问答的**措辞**，返回纯文本；
- 所有写入都走 `repository.logFood / logWeight / …`，参数由 UI 或确定性解析器给出；
- 营养数值没有任何一处来自模型输出。
