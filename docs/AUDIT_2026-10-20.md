# 全局审查报告（2026-10-20 · v3.9.0）

审查方式：静态扫描 + 代码走读 + 现有测试与实测记录核对。
**未做**：真机运行、性能采样、TalkBack 走查（原因见末尾）。

## 二、代码层

### 高优先

**H1 大文件（拆分就能降 bug 率）**

| 文件 | 行数 | 问题 |
|---|---|---|
| `DietSportScreen.kt` | 1,072 | 饮食/运动两个页面 + 5 个弹窗 + 10 个行组件全在一个文件 |
| `EditSheets.kt` | 663 | 6 个编辑弹窗堆在一起 |
| `SettingsScreen.kt` | 618 | 页面 + 分组 + 若干行组件 |
| `HomeScreen.kt` | 572 | 页面 + 卡片 + 习惯区 |

**H2 128 处硬编码中文（英文用户会看到中文）**

抽样：
```
ReportImageExporter.kt: "OmniHealth · 本周复盘" / "纤维达标 X/7 天" / "分享周复盘"
AiAdvisor.kt:           中文 system prompt（对英文用户也发中文提示词）
OfflineAiEngine.kt:     "近 N 天概览" / "健康分 …" / "步数 …"
Entities.kt:            unit 默认值 "次"
```
后果：切到 English 后，**离线 AI 报告与导出图片仍是中文**，这是能直接看到的缺陷。

**H3 31 个未使用字符串资源**

`save/cancel/done/back`、`home_bmi/home_tdee/home_habits`、`stats_weight`、`ai_error`、`widget_title`（被 XML 引用，脚本未统计）等。
属于历史遗留，留着会让人误以为还有对应功能。

**H4 domain 层混入 Android 依赖**

`StepSensorManager` 直接依赖 `SensorManager`，导致 domain 包不能纯 JVM 测试。
它不是纯逻辑，建议移到 `data/sensor/`，让 domain 只留可测的计算。

### 中优先

**M1 656 处硬编码 dp/sp**：没有设计令牌（spacing/type scale），改一次全局间距要改几十处。

**M2 可访问性**：8 处 `contentDescription = null`、12 个 `Icon` 无描述。图标重的地方（底栏）靠文字兜住了，但纯图标按钮对读屏不可用。

**M3 错误处理**：`runCatching{}.getOrNull()` 用得很多，但**没有一处把失败告知用户**（除了 AI 的 insecure_endpoint）。数据库写入失败、导出失败目前是静默的。

### 低优先 / 表现良好

- 无 `!!`、无 `GlobalScope`、无 `runBlocking`、无 `printStackTrace`、无空 catch 👍
- 无 TODO/FIXME 残留
- domain 计算全部纯函数且有测试（HealthCalculator 14、MealParser 6、MealPlanner 5、TrendInterpreter 4、WeeklyReview 5、Backup 2、AiEndpoint 4、OfflineAi 5 = 45）

### 有意不做的拆分

`DietSportScreen`（563 行）没有继续硬拆。它的主体是两个标签页的 `LazyListScope` 内容块，依赖十余个闭包参数；
机械切分只会把耦合藏进参数列表。要真正降下来，需先把「标签内容」重构成接收 `DietTabState` 数据类的组件——属于设计改动，不是搬代码。
