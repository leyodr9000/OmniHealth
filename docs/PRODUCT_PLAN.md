# 产品计划：从「能用」到「愿意每天用」

> 研究方法：公开资料 + 竞品分析文章 + 本项目管理论文档。
> **没有**做竞品 App 的逐项功能核验，也没有用户访谈数据；凡属推断都会标注。
> 本文只做规划，不含实施。

## 一、从对标里读到的三件事

### 1. 留存来自「记录成本」与「转换成本」，不是功能数量

一份 2020 年的[薄荷健康产品分析](https://www.163.com/dy/article/FADQOSSI0511805E.html)引用的易观 2019 年 7 月数据里，薄荷**次月留存 86%**，而 Keep 与妙健康相近、乐心更好一些。作者把薄荷的高留存归因于「长期记录 + 数据反馈」：

> 用户也因为该产品有自己的日常生活记录……使用户转换成本增高，因此流失率较低。

同一篇文章的用户访谈里，抱怨集中在**入口**而不是功能缺失：

> 每一个常用功能都不能直接点开，还有一些隐藏的比较深，这大大提高了用户使用的门槛

对我们的直接含义：**我们缺的不是功能，是"一步就能完成"的路径**。v3.4.0/v3.5.0 做的最近常吃、复制上一餐、我的套餐，正是这一条。

### 2. 健康类产品天然低频，靠「反馈」拉回

同一篇分析的结论是：

> 健康不属于高频次消费产品，因此这类的产品需要任务和计划来提高用户粘性与活跃度

竞品用任务、圈子、排行榜解决"回来"的问题。**我们不该照抄**：那套机制依赖社区与运营，且与「减少焦虑」的定位冲突。我们可以用**低频但确定的反馈**替代——每周一次有依据的复盘、每天一次可见的完成度。

### 3. 竞品的护城河在数据资产，不在 UI

- 薄荷：食物库 + 营养数据 + 长期记录
- Keep：课程内容 + 社交关系链
- MyFitnessPal：食物库规模 + [跨天复制餐](https://support.myfitnesspal.com/hc/en-us/articles/360032622131-How-do-I-copy-a-meal-from-one-day-to-another) / [Saved Meals](https://support.myfitnesspal.com/hc/en-us/articles/360032625331-Create-find-and-log-your-saved-meals) 这类"减少重复劳动"的基础设施

我们的食物库只有 211 条，这是**最硬的短板**：再好的记录流程，搜不到要吃的东西就断了。

## 二、我们的定位判断

| 维度 | 竞品主流 | 我们应有的选择 |
|---|---|---|
| 粘性来源 | 社区、打卡、排行榜、课程 | **记录成本最低 + 结论有依据** |
| 商业化 | 商城、会员、课程 | 不做（个人项目，无供应链） |
| 数据规模 | 数万食物 + 品牌 | 短期做不了，靠"自定义 + 常吃"兜住 |
| 情绪设计 | 连续打卡、排名、减重竞赛 | **明确不做**，避免制造焦虑 |
| 可信度 | 多数只给数字 | **我们领先**：覆盖度、缺失说明、结论依据 |

一句话：**不跟竞品比"热闹"，比"账算得清、记得省事"**。

## 三、三阶段计划

### 阶段一：把"断点"补上（决定会不会用第二次）

| 项 | 为什么 | 判定标准 |
|---|---|---|
| 桌面小组件 | 记录类产品最高频的入口；没有小组件，打开 App 这件事本身就要靠意志力 | 桌面可见今日热量/剩余，点进去直达记录 |
| 记录提醒 | 竞品访谈里的高频诉求是"容易忘"；我们已有 WorkManager 基础设施 | 晚间提醒可开关、可设时间 |
| 食物库扩充 | 搜不到 = 直接放弃；这是最硬的短板 | 至少覆盖常见主食/蛋白/蔬果 + 外卖高频品 |
| 份量双单位 | 竞品用"份/碗/个"，我们只有克 | 记录面板可切「克 / 份」并显示换算 |

### 阶段二：把"反馈"做厚（决定会不会用一个月）

| 项 | 为什么 | 判定标准 |
|---|---|---|
| 周报可分享（图片） | 访谈显示用户想分享周/月总结，但不愿发朋友圈 | 生成本地图片，可存相册/分享 |
| 目标达成率趋势 | 现在只有单日达标，看不到"这周比上周好" | 7/30 天达标率曲线 |
| 体重与摄入的关联视图 | 用户最想知道"我吃这些，体重怎么变的" | 双轴图 + 一句不带因果的说明 |
| 数据体检 | 主动指出"你连续 5 天没记早餐" | 复盘卡已有的能力扩展到 30 天 |

### 阶段三：把"省事"做到极致（决定会不会推荐给别人）

| 项 | 为什么 | 判定标准 |
|---|---|---|
| 条码扫描 | MFP/薄荷的核心效率功能 | 扫包装条码 → 命中或新建自定义食物 |
| 外卖/连锁菜品包 | 中国用户真实场景 | 内置 30–50 个常见菜品组合 |
| 语音记餐 | 手上有油的时候最有用 | 语音转文字复用现有解析 |

## 四、明确不做（以及为什么）

| 不做 | 原因 |
|---|---|
| 社区 / 好友 / 排行 | 需要运营与审核，且与"减少焦虑"冲突 |
| 会员 / 商城 | 无供应链，会毁掉可信度 |
| 连续打卡惩罚 | 竞品常见，但对长期使用是负向的 |
| 云同步 / 账号 | 隐私与合规成本高，本地优先已能满足个人使用 |
| 训练课程 | 内容生产成本高，且不是我们的差异化 |

## 五、优先级排序（按"单位工作量带来的留存提升"）

1. **桌面小组件**——最高频入口，工作量中等（原生 AppWidget）
2. **食物库扩充**——最硬短板，工作量取决于数据来源
3. **记录提醒**——基础设施已有，工作量小
4. **份量双单位**——记录面板改动，工作量小
5. **周报图片分享**——本地绘制 + 分享，工作量中等
6. **条码扫描**——依赖第三方库，包体与维护成本需评估
7. 其余（关联视图、数据体检、语音）——后置

## 六、风险与前置条件

- **真机性能仍未采集**：小组件与图表会增加渲染负载，先有基线再往上加东西更稳。
- **食物库数据来源**：自建成本高；需要考虑是否有合规可用的公开数据，或只做"用户自定义 + 常吃"。
- **条码扫描**：ML Kit 会显著增大包体（当前 2.08 MB），与"轻量"定位冲突，需要明确取舍。
- **单机无反馈渠道**：没有崩溃上报，任何新模块都要靠手动验证；这也是为什么阶段一的每一项都应该小而可回退。

## 七、下一步建议

先做**阶段一的前两项**（小组件 + 记录提醒），因为：
- 都不依赖新数据源；
- 都能在离线状态下工作；
- 都直接作用于"每天打开一次"这个最关键的动作。

食物库扩充需要先决定数据来源，这是产品决策不是工程决策，建议单独讨论后再动手。
